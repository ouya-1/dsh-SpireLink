# 界面清单：MCP 必须能识别的每一个画面

目标：**任何画面下 `legal_actions` 要么给出合法动作，要么明确说明"我在等什么"，绝不能静默返回空数组让 agent 无限轮询。**

这份清单是从 `lib/desktop-1.0.jar` 的枚举字节码里抠出来的，不是凭印象列的：

- `AbstractDungeon$CurrentScreen`（24 个）：地牢内的画面。
- `MainMenuScreen$CurScreen`（22 个）：主菜单及其子画面。
- `AbstractRoom$RoomPhase`（4 个）+ 房间类型：房间级状态，决定"同一画面不同阶段"。
- `RewardItem$RewardType`（7 个）：奖励条目种类。

## 返回体积契约（2025-11 起）

| 界面 | 默认区块 | 目标体积 |
|---|---|---|
| 战斗 | meta/player/potions/memory/combat（hints 仅未就绪 / 上次 act 被拒 / 自带异常标记） | ≤ 6,000 字符/步（含 legal_actions） |
| 事件 / Neow | 同上 + event(+neow) | ≤ 6,000 |
| 商店 | 同上 + shop | ≤ 6,000 |
| 奖励界面 | 同上 + rewards/boss_reward/card_reward | ≤ 6,000 |
| 地图 | 同上 + map（整幕，节点精简） | ≤ 12,000 |

- `include` = 白名单（meta + 所给区块），`exclude` = 从默认集合里减；契约写在 `skill/spirelink/references/tools.md`。
- `map[]` 节点只保留 `{x,y,symbol,room,taken?,edges:[[x,y]]}`，其余字段一律由它们推导。
- `memory.briefing` 只在开局/换幕/(主菜单|选人|死亡|胜利) 各给一次（`include:["briefing"]` 可以单独要，返回顶层 `briefing`）；`hints` 只在上次动作被拒、未就绪、或自带异常标记（`map_no_reachable`/`suggest_note`/`unknown_ui`/`event_missing`）时给，**ready、无错且没有这些标记时整块不存在**。
- `include`/`exclude`：未知块名忽略；`meta` 永不可排除；`exclude` 压过 `include`。`exclude:["hints"]` 能真删掉。
- 采样脚本：`python 内部验收脚本（未随仓库发布） --samples 6`（打印每屏总字符、各段字符、legal_actions 与 include/exclude 对照）。

## 不变式（P2.5 必须先落地）

| # | 规则 |
|---|---|
| I1 | `ui` 只由「画面枚举 + 房间阶段 + 关键子状态」推导，不猜 |
| I2 | 未映射的画面 → `ui="unknown:<ScreenName>"`、`ready=false`、`hints.unknown_ui=true`、debug 日志打一次（不刷屏） |
| I3 | `ready=true` 时 `actions` 必须非空；空数组只能出现在 `ready=false`（过渡/未知/全局禁止操作） |
| I4 | 每个 `ui` 至少有一个"退出这个画面"的动作（`proceed`/`leave`/`confirm`/`cancel`），除非它是终局（`run_over`） |
| I5 | 新增画面枚举值时，必须同时更新本文件与 `get_state.meta.ui` 的映射注释 |

## 二、房间级状态（RoomPhase + 房间类型）

同一个 `NONE` 画面在不同房间里含义完全不同，`ui` 必须细分：

| 房间类型 | `ui` | 需要的动作 | 状态 |
|---|---|---|---|
| `MonsterRoom` / `MonsterRoomElite` / `MonsterRoomBoss` + `COMBAT` | `combat` | `play_card` / `end_turn` / `use_potion` / `discard_potion` / **`abandon_mid_run`（永远最后一条，标签「放弃本局（删存档并回主菜单）」，只在能操作帧出现；#122·C13-03）** | ✅ 实测（`monster`/`elite`/`boss` 房间通过）。`combat` 区块另带 `energy`/`energy_max`/`playable_cards`（#123·C14-05）；**`play_blocked` 恒定存在**（#124·C15-05）：有阻塞时是一句「能量不足…play_card 因此不在 legal_actions 里，不是接口出错」，没阻塞时是 `null`。**刚进战斗头几帧**（#125·C16-04，`combat_settling`）`ready:false` + `awaiting:"transition"` + `blocked_ui:"combat"`（怪还是 `Intent.DEBUG` 占位、手牌空），**4 秒安全上界**，等意图滚出来再动手 |
| `RestRoom` | `rest` | `rest` / `smith` / `lift` / `toke`，`proceed` **有时有有时没有** | ✅ 实测。**一次性**：一个篝火只能用一次选项；选过之后只给 `proceed`，再 `rest`/`smith` 返回 `ILLEGAL_ACTION`「篝火选项已经选过了」。`proceed` 只在「继续」按钮真可见时出现（取决于剩余可用选项），所以同一屏两次读到的动作集合可能不同——以 `legal_actions` 为准（issue #97·C3-09） |
| `ShopRoom` | `shop`（未开屏时 `shop_room`） | `buy` / `purge_card` / `leave` / `open_shop` | ✅ 实测（`buy`/`leave` 通过）。`purge_card` 只在「这一家还没净化过（`purge.available`）且金币 ≥ `purge.cost`」时出现；**每家商店各一次**，价格随本局净化次数上涨（75 / 100 / 125…，`ShopScreen.purgeCard()` 每次 +25） |
| `EventRoom`（含 `NeowRoom`） | `event` / `neow` | `choose_option{index}` / `event_continue` / `proceed` | ✅ 52/52 事件通过（`get_state.event` 给 `id/name/body/options[]/text_typing/text_source/note`）。**打字期不挡动作**：`text_typing:true` 时 `ready` 仍是 `true`，`choose_option` 照发能成功（issue #97·C3-04）。**`event` 区块按房间给、不按 `ui` 给**：事件结算后在 `ui=map`/`ui=combat_reward` 也可能看到旧 `event`，判界面只看 `meta.ui`（issue #97·C3-03） |
| `TreasureRoom` | `treasure` | `open_chest`（**实测那一拍只有它**；`proceed` 仅当宝箱开完、奖励领净、`canProceed()` 为真才出现，实测没出现） | ✅ `open_chest` 实测通过。别把 `proceed` 当「随时可用」：手动发能过，但那是绕开 planner（issue #92）。**Boss 宝箱房 `TreasureRoomBoss`（第 1/2 幕）同属 `ui=treasure`**（#114）：先 `open_chest`（`BossChest.open()` 才开 `boss_reward`），领完 Boss 遗物才给 `proceed`「继续（离开本幕）」（`goToNextDungeon`）；没领就走 → `NOT_READY`「先 open_chest 开 Boss 宝箱并 claim_relic，现在走会丢遗物」。**`proceed` 走 `goToNextDungeon` 且带 2 秒过场预算**（#118）：预算内重发 → `NOT_READY`「上一段 Boss 过场刚开始（已等 Nms / 预算 2000ms）…请等状态变化后再看 `legal_actions`」；`isDungeonBeaten` 已置 → `NOT_READY`「正在切下一幕…轮询 `get_state` 直到 `ui` 不再是 treasure」；**绝不会「回 ok 但没动」导致 `queued` 卡死** |
| `VictoryRoom` | `victory` | `proceed` | ⬜ 待通关长跑 |
| 事件文字打字中（`room.phase==EVENT` 且无选项） | 沿用当前 `ui` | `event_continue` 推进 | ✅ 无选项时给 `event_continue`（不再 `ready=false` 死等） |

### 人类只读界面：主菜单便签面板（#46）

- **谁用**：只有人类。`MainMenuScreen.render` postfix 在主菜单左下角画「便签（N）」入口，点开是半透明遮罩 + 居中只读面板：每页 12 条，按 `updated_at` 倒序，每行 `[类型] 名称：正文`，右上角「第 x/y 页 · 共 N 条」。
- **翻页**：滚轮 / ↑↓ 逐行，PgUp/PgDn 整页，Home/End 首尾；ESC、点面板外空白、再点入口都能关。
- **对 agent 无感**：不新增 MCP 工具，`tools/list` 仍是 9 个常驻工具；`ui` / `legal_actions` 不变；面板只调 `Notes.list(null)`，从不写 `notes.json`（只读）。
- **开关**：`config.properties` 的 `notes_panel`（默认 `true`）。
- **副作用**：面板打开时吞掉左键与 ESC（避免误触「单机游戏」等原按钮），这段时间 agent 的模拟点击也会被吞掉，直到人类关掉面板。

## 四、奖励条目（RewardItem.RewardType）

| 类型 | 说明 | 处理 |
|---|---|---|
| `CARD` | 选卡 | `take_reward` → 进 `card_reward` |
| `GOLD` / `STOLEN_GOLD` | 金币 | `take_reward` 直接结算 |
| `RELIC` | 遗物 | `take_reward` 直接结算 |
| `POTION` | 药水 | `take_reward` 直接进腰带。**槽满时没有 `potion_discard` 屏**（issue #112·C8-05）：这条奖励 `takeable=false` + `blocked_reason`，`legal_actions` 不给它的 `take_reward`，硬发 → `POTION_SLOT_FULL`「药水槽满了，拿不了这瓶药水；先 `discard_potion{"slot":N}` 丢掉一瓶再回来拿（可丢: 0=香蕉, …）」。**#116a 起这一屏同时广告那些 `discard_potion`**（每个 `canDiscard()` 的槽一条），所以「先丢一瓶」本屏就能执行 |

- **`player.energy` / `energy_max` 非战斗态是 `null` + `energy_note`**（#124·C15-04）：说明「能量只在战斗房里有意义（原版面板会保留上一战的数字）」，别当漏字段。
- **腰带满时 `rewards` 多一个 screen 级 `potion_blocked`**（#123·C14-06）：整段话说明「药水槽已满（3/3）：药水奖励要先用 discard_potion 丢一瓶才能领，丢完再读 legal_actions 就会出现 take_reward；现在直接 proceed 等于放弃这份奖励（含钥匙/遗物）」。它只是解释，`take_reward` 不会因此出现 —— 先 `discard_potion` 再重读 `legal_actions`。
- **奖励屏的行比房间奖励可能多一条**（#120·C11-02 / C11-06）：原版 `CombatRewardScreen.setupItemReward()` 只在**普通房间**往屏幕列表追加一条 CARD「将一张卡牌加入你的牌组中」（`TreasureRoom` / `RestRoom` / `noCardsInRewards` 的事件不加）。每行都带 `type`，**领之前先看 `rewards.items[].type`**：`CARD` 行 `take_reward` 只是打开 `card_reward` 屏。dev 工具回包的 `rewards` 也是**屏幕行数**（= `get_state.rewards.count`），`room_rewards` 才是房间列表条数，`rows` 给每行 `{index,type,text}`。
- **`STALE_VERSION` 的话术分两支**（#120·C11-05，码不变）：带**比现场旧**的版本 →「已过期（当前 M），重新取法律动作」；带**比现场新**的版本（还不存在）→「比当前版本（M）更新：这个版本号还不存在…按最近一次读到的 M 重发」。
- **`match_game` 的 `PLAY` 屏**（#120·C11-04）：常规是每张可翻的牌一条 `choose_match_card`；棋盘 8 秒没动时会**同时**多给一条 `proceed`「放弃小游戏并离开（会损失奖励）」，`game_done` 后是 `proceed`「完成小游戏」。**`proceed` 在这里 = 放弃奖励**，别当退出对话用。
- **并发两条 `act`**（#120·C11-07 结论口径，**#125·C16-02 收紧**）：同一个 `state_version` 上连发两条，第二条**要么 `ACTION_IN_FLIGHT` + `queue_status:"BUSY"`**（第一条真的在落地：`ActionInFlight` 里压着东西），**要么 `NOT_READY`**（队列忙但没有动作在飞 —— 主线程被过渡/动画那一帧占着，message 是「主线程正忙着执行别的东西…」），两种都不是 `BAD_REQUEST`，也不会两条都执行。诊断字段在回包顶层与 `error.*` **各有一份**（`error.queue_status` / `error.waited_ms` / `error.version_advanced` / `error.retry_after_ms`，#120·C11-01）；`retry_after_ms` **只有墙钟护栏那支有**。
- **提交型动作的回包是 `applied` + `settled:false`**（#123·C14-01/02/03）：`continue_run` / `embark` / 放弃类（`abandon_run`/`abandon_mid_run`/`confirm_abandon`）—— 点击已交出去、世界在过渡：回包 `ready:false` + `actions:[]` + `awaiting`（`loading`/`transition`）+ `log` 写「已提交…不要重发」。**只有这些回包带 `settled`（恒 `false`）**；别重发、别当失败，只轮询 `get_state`。**回包耗时 0.55~0.70 s**（一次主线程执行 + 一帧过渡，不是 ~0.1 s），验收写成「**≤1 s 且 `outcome` 不是 `queued`**」。
- **放弃本局的 0.8~1.6 s 过渡期**（#123·S2，`RunExitWindow`，上界 10 s）：实时帧 `ui:"other"`、`ready:false`、`blocked_ui:"other"`、`awaiting:"transition"`，三个入口都回 `NOT_READY` +「正在离开本局…旧地牢的 ui 与动作表已经不作数…轮询 get_state 直到 ui=main_menu 且 ready:true」；**`act` 的拒绝也带 `blocked_ui:"other"` + `awaiting:"transition"`，`ui` 取读接口同一拍的实时值**（#124·C15-01）；**别照上一帧的地图/战斗动作表动手**（否则拿到 `ILLEGAL_ACTION: ui=main_menu 下不能执行 …`）。
- **存档载入窗口**（#121·C12-01 / #122）：`continue_run` **或 `embark`** 交出去到 run 屏出现之前（**判据 v3：我们自己的打点 + 状态层 `ui` 仍是 `main_menu`/`char_select`/`mode_select`/`other` + 30 s 上界；不看 `loadingSave`，v1 已证伪**），`meta.ready:false` + `meta.awaiting:"loading"`，三个入口（`get_state` / `legal_actions` / `act`）都回 `NOT_READY`，文案「存档正在载入（continue_run 已点，战斗/地图还没出来）…不要重发 continue_run；轮询 get_state 直到 ready:true」，`actions:[]`、`get_state`/`legal_actions` 顶层 `blocked_ui` —— 这一拍**不会**再把 `continue_run` 广告成合法动作。**读操作在这里走 500 ms 短超时**（#123·C14-03，主线程在建地牢），每一拍都从缓存回一帧 `NOT_READY` + 载入文案 + `awaiting:"loading"`（缓存里的 `awaiting` 会被改写，不会骗你说 `playing`）。
- **刚进战斗的 `combat_settling`**（#125·C16-04）：进战斗房头几帧，怪挂占位意图 `Intent.DEBUG`（`monsters[].intent.id == "DEBUG"`、`unknown:true`），手牌空、能量面板没填。判据 = 「COMBAT 房里还有活怪 `intent == DEBUG`」，`ready:false` + `awaiting:"transition"` + `blocked_ui:"combat"`，`legal_actions` 是 `actions:[]` +「ui=combat 游戏还没静止…」；4 秒（`SETTLING_MAX_MS`）后强制按常规规则判，不会永远卡住。**这一拍别出牌/别 end_turn**，等 200~500 ms 再读。
- **拒绝优先级**（#121·C12-03，`ToolCatalog.preflightRejectionCode`）：`NOT_READY`（载入/崩溃）→ `STALE_VERSION` → `ACTION_IN_FLIGHT` → 交给执行器（`ILLEGAL_ACTION` 等）。版本不对时**永远先拿到 `STALE_VERSION`**，不会先吃执行器的屏幕级拒绝；原则是「谁离执行器越远、谁先说话」。
- **所有 `act` 拒绝回包都带 `ui` / `ready` / `actions`**（#121·C12-02）：默认 `ready:false` + `ui` 取缓存快照 + `actions:[]`；`STALE_VERSION` 与执行器拒绝会换成**新鲜计划**（`ready` 可能是 `true`）。**过渡窗口里（载入/放弃）还带 `blocked_ui` + `awaiting`**（#124·C15-01）：`ui` 改用读接口同一拍的实时值（`other`），`blocked_ui` 同值，`awaiting` 是 `loading`/`transition`——三个入口对同一拍的描述一致。`get_state` 的未就绪回包也在**顶层**给 `blocked_ui`（#121·C12-04，与 `legal_actions` 对称；`meta.blocked_ui` 仍是嵌套那份）。
- **奖励屏（`combat_reward`）2026-11-03 的三处口径**：#116a 腰带满的那拍会额外广告 `discard_potion{slot}`（每个 `canDiscard()` 槽一条），`POTION_SLOT_FULL` 文案带 `discard_potion{"slot":N}` + 可丢清单；#116b 钥匙奖励 `take_reward` 是**真领取**且**不吞同屏遗物**（切断原版 `relicLink` 互斥，钥匙照领、遗物照留）；#114 Boss 战后的 `proceed` 进 **Boss 宝箱房**（`goToTreasureRoom`），不是打开地图。
- **peek 不是决策点**（#115）：`get_state{include:["deck"|"discard_pile"|"exhaust_pile"|"draw_pile"]}` 真的会开视图屏 4 秒，但**这 4 秒 `meta.ui` 与 `legal_actions` 和 peek 前完全一致**（商店里仍是 `buy`/`purge_card`/`leave`）。这不是「人类自己点顶栏」那种 `tutorial_tip`（那种要用 `dismiss_tip` 关，见 §一 `FTUE` 行）。

## 八、已知边界（第 2 轮 QA 实测，2026-11-03）

1. **`main_menu` 的 `open_mode_select` 偶发「回了 `queued` 但界面没变」**（issue #94·B2-19）：5 次里 2 次回 `outcome:"queued"`，`get_state` 却仍是 `main_menu`、`state_version` 也没动 —— 等于白点一下，再发一次才生效。**怀疑**与便签面板有关：那几行 HUD 文字画在按钮上方，点击被 HUD 吞了（未确认，也没有日志证据）。
   - 现在的做法：`open_mode_select` 回 `queued` 且 `get_state` 还是 `main_menu` 时，**最多再发 2 次**；别连发，也别把它当 `ILLEGAL_ACTION`（动作没被拒，只是没落地）。
   - 同一类现象在别的纯 UI 按钮上理论上也会有，遇到就按「重发 + 看版本」处理。
2. **`treasure` 的 `proceed` 不在 advertised 集合里**（issue #92）：那一拍只给 `open_chest`。手动发 `proceed` 能跑通，但那是绕开 planner；文档只写 advertised 集合。
